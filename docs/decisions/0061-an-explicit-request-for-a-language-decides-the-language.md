# 0061. An explicit request for a language decides the language, not the language the message is written in

- Status: Accepted
- Date: 2026-10-11
- Amends: 0051 (what decides the stored language) and 0047 (a request to switch is now read by code)

## Context
In a real Haiku 5.5 demo chat (2026-10-11, Application `app_01M4NHRWCFZER208JCM02HT7Z5`), a Spanish Candidate in Spain, asked "¿Qué disponibilidad tienes?", wrote "me preguntas en inglés porfi" (ask me in English, please). The Jev router read the message as `lang: es` (confidence 0.99) and `switch: 0.15`: the message is written in Spanish and is not "a full sentence in a different language". By 0051 the language therefore stayed `es-ES`. The agent, which follows the Candidate, nonetheless replied in English; the buttons (built by the backend from the stored language) stayed Spanish ("Jornada completa…"); the record said es-ES. Reply, buttons and record disagreed. The Candidate's next message, "mejor espa;ol", was read the same way and also changed nothing, so the language only came back because the agent happened to follow.

The cause is the question, not the threshold. 0051's battery reads the language a message is written IN. An explicit request names the language it ASKS FOR, and the two are different facts: a request to switch to English can be written in Spanish, and a request for Spanish can be written in English.

## Decision
- **A new typed question, `asks`.** A Choice over `es`, `en` and `none` ("does `latest_candidate_message` ask for the conversation to continue in a particular language from now on, and in which?"), with `what` / `not_for` / `examples` on each option. It is the seventh question of the same request (they run in parallel, so the six others are unchanged and the call is still one). The focus says that only an explicit request counts: writing in a language, mentioning one ("trabajé en inglés", "hablo inglés y español"), asking what the job needs, or a language name on its own are `none`.
- **Decided in policy code.** `criba.jev.policy.decide_language`: when `asks` is `es` or `en` with confidence of at least `Thresholds.ask_confidence` (0.80), that language is the target, whatever language the message is written in, on the first message and after it. English is `en`; Spanish is the Application's country variant (`es-ES`, `es-MX`), as `spanish_for` has always done. A request for the language already stored changes nothing but a stale Spanish variant (`request_same`). Below the threshold the request does not exist and the written-language rules of 0051 apply exactly as before.
- **0047 holds.** One word, a name, a place or a number still never switches; a language name on its own is `none` in the question's criteria, and a low-confidence request falls through to the unchanged rules. The written-language switch (`lang` and `switch`) is untouched, and the request wins only when it clears its own threshold.
- **One turn.** The step stores the decision before the run, so the agent reads the new language from `get_application`, the buttons (`pending_choice`, built from the stored language) and the record agree on the same turn. Nothing is added to the input the agent receives.
- **What is kept.** `message_signals` gains three columns by migration `0010` (additive, `ALTER TABLE ... ADD COLUMN`; `contracts/schema.sql` updated): `asks` and `asks_confidence` (the question's answer), and `language_reason` (`first_message`, `switch`, `request` or `variant`, set only when the message stored a language). Codes and probabilities, no text, the same retention and the same rule that nothing decides from them (0051). No new event kind: `events.kind` has a CHECK that needs a table rebuild to extend (as 0057 found), and the signals row already says what was read and what was set.
- **Spoken turns** (spoken-checks R9) still never change the language; their `asks` reading is stored and ignored for the record.
- **Thresholds** are versioned: `Thresholds.version` is now `jev-1.13-v2`. `ask_confidence` was fitted on labelled messages against the real service (`docs/evidence/jev-calibration.md`): 30 new messages (requests in both directions and in both Spanish variants, mentions that are not requests) plus 4 existing ones that are requests. On dev every cut-off from 0.30 to 0.90 gave the same decisions (13 of 13 requests, 0 false), the lowest confidence of a correct request was 0.94 and no non-request gave a request option more than 0.05. On holdout 7 of 8 requests were caught and none invented; the one missed, "mejor espa;ol" (the demo's second message, with its typo), read 0.30. A false switch is the costly error, and a missed request is repaired by asking again, so 0.80 sits in the middle of the empty gap.

## Alternatives considered
- **Make the existing `switch` Noul broader ("or asks to switch"):** it would merge two judgments (written language, asked language) into one, which the workflow rules say to avoid, and it could not tell which language is wanted.
- **Detect "en inglés" and the like in code with word lists:** rejected by 0042 and 0047 for the same reason as before (it fires on "trabajé en inglés").
- **Trust the agent to switch and have it report the language:** that is what 0051 took out of the model's hands; here the agent followed the Candidate while the buttons and the record did not.
- **A four-way `asks` Choice with `es-ES` and `es-MX`:** the variant follows the country, so it only dilutes the confidence (0051).
- **A sticky request (ignore written-language switches after an explicit request):** not decided here. A Candidate who asks for English and then answers in full Spanish sentences gets switched back by the existing `switch` rule. It keeps 0051's written-language logic as it is; whether a request should hold until the next request is a product decision for the owner.

## Consequences
- **Contract** (additive): `contracts/schema.sql` gains three nullable columns on `message_signals`; migration `0010`. The OpenAPI files are unchanged (`message_signals` on the Application detail still carries flags and no probability).
- **Cost and latency:** one more Choice in the request: about 2,100 input tokens (was 1,650) and $0.000088 a call (was $0.000069); p50 0.29 s, p95 0.41 s in the new calibration run.
- **Simulator:** the stub Jev answers `asks` from "en/in <language name>" plus a request cue; persona `language_request_es` (Spain, asks for English at the licence question, ends on `en`).
- **Tests:** `tests/jev/` (policy table, router step with buttons and the signals row, client parsing, post-reply mode), `tests/db/test_migrate.py` (0009), `src/tests/sim/stub_llm/test_jev.py`, `src/tests/jev_calibration/` and the live flow `language_request`.
- **Known gap:** a request is recognised in English and Spanish only; another language is `other` as before and asks nothing.
