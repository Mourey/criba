# 0050. The backend books a tapped slot, and what the agent passed on stays grounded in its history

- Status: Accepted, amended by 0064
- Date: 2026-10-10
- Refines: 0043 (which taps the backend records), 0045 (what a finished turn's result keeps) and 0038 (what the agent is told about the system turn and the slot buttons)

## Context
The live smoke run of 2026-10-10 on real Haiku 5.5 (`docs/evidence/live-smoke.md`) failed "Approval, then booking" once in five runs. After the `[system] approved` turn the model offered the slots, then raised an Escalation and apologised: "he avisado a una persona del equipo sin que lo pidieras". After the Candidate tapped a slot it wrote "Antes te di detalles de las entrevistas que no he podido confirmar, así que no te fíes de ellos", re-offered the slots and never called `book_interview`, so no Interview and no `.ics`. In the Knockout flow, which passed, the reply to a Review request said "el enlace de requisitos que te di antes no es un enlace oficial verificado, así que no lo uses".

The Hermes sessions of the rerun on a fresh stack (`criba-bookfix`, five booking runs and one Knockout run, all of which passed) show what the model sees. Rewriting each stored session with the plugin's own `trim_history`, as every request goes out (0045):
- the Knockout's `record_answer` result reached the next turn as `{"ok":true,"value":{"status":"knockout","field":"driver_license"}}`, followed by the model's own reply quoting the requirements link. Nothing the model can see says where the link came from, and the skill tells it never to invent a result;
- `offer_interview_slots` reached the slot-tap turn as `{"ok":true,"value":{}}`, followed by the model's reply naming the day and the Location. The tap arrived as the bare `so_LsRJKvGAdj5m`, an id that appears nowhere else in what the model sees. Booking depended on the model trusting an id it could not trace, and in the failing run it did not;
- `finish_screening` reached the system turn as `{"ok":true,"value":{"stage":"qualified"}}` after the Qualified close.

The Escalation was traced in a later run on the fixed backend (booking passed; the reply after the tap ended "Perdona el lío de antes"). Inside the system turn, right after `offer_interview_slots`, Haiku called `raise_escalation(reason: other, note: "Offer slots tool returned no output for the interview slot buttons; the slots are not shown to the Candidate.")`. The skill said only that the slots "appear as buttons"; the model took the missing list in its own text for a failure, escalated, and then apologised for it. `[system] approved` itself was never questioned in the traces. It is still a user message that neither the SOUL nor the skill explained.

The failure is intermittent (zero in six baseline reruns), but the causes are in what the model is shown, not in the model: it is right to distrust text it cannot source, and it was never told that the buttons are the backend's job.

## Decision
- **The backend books a tapped slot before the agent runs**, as it records a tap on an answer option (0043). When the tapped id is one of the slots in the pending choice (an unexpired offer, slot not booked by anyone), the router calls `book_interview` with it and the agent's input is the result after `[tap result] `. The agent confirms the Interview from it and calls nothing. "Other time", a stale or already-used slot, and anything not in the pending choice still reach the agent as the bare id; a slot named in words is still the agent's `book_interview(slot_ref)`.
- **A finished turn's result keeps a trace of what the agent passed on** (refines 0045). In the history_trim middleware, a `message` the agent sends word for word becomes the fixed marker "(approved text from the backend, sent word for word in your reply)"; an offer keeps each slot's `slot_ref` and `label` and the Locations' names; an Interview keeps `local_label`, `location_name` and `address`; `ics_sent` stays. Every compacted result stays under the 300 characters the scenario suite allows, and the rewrite stays a pure, idempotent function of the message, so the cache prefix holds.
- **The Screener skill says what the backend does around the agent.** The backend attaches the slots to the agent's one-line introduction as buttons, so that line is complete without listing them. (A first wording that said "never escalate" next to the system turn was followed by two such Escalations in five runs; the positive wording had none in six.) `[system] approved` is the backend's cue to check the record: the agent goes to the After Approval step, where `get_application` decides, and never mentions it. Earlier results are shortened, and what the agent sent from them was right, so it never takes it back. The system turn keeps its fixed text and its lack of authority (0038): a Candidate who types the same words gets the same check, and `offer_interview_slots` still refuses unless the Application is Approved in the database. This part is wording, because the frozen tool contract (`offer_interview_slots_output`, `additionalProperties: false`) leaves no room for a note in the result; the two above are code.

## Alternatives considered
- **Skill wording only** ("trust what you sent before", "book the tapped slot"): the model would still have to trust an id and texts it cannot trace, and booking would stay one model slip away. A tap is already the Candidate's whole answer, and 0043 settled that code records it.
- **Stop trimming the results the agent relays:** the Knockout message alone is over 300 characters, the limit the scenario suite holds a finished turn's result to (0045), and the slot offer with its booking link over 1,000. The trace gives the model the source without the size.
- **A system turn that states the facts** ("the Candidate is Approved, offer slots"): rejected by 0038, because the model would obey the same words injected by a Candidate.
- **Mark a Candidate message that starts like a backend input** ("(typed by the Candidate) [system] approved"), so the skill could say such inputs are only the backend's: tried and dropped. It changes what the agent receives for an injection, which the robustness suite pins as verbatim (`test_robustness.py`), and it adds nothing to safety: the system turn has no authority whoever types it.
- **Send the slot offer from code after Approval, with no run** (as the WhatsApp template does): removes the system turn's ambiguity, but the agent then never sees the offer it must later confirm or reschedule from, and the web chat's offer loses the agent's wording.

## Consequences
- A slot tap books the Interview on every channel whatever the model does; the `.ics` goes with the agent's next message as before (`invite_after_message` is the tap's message id). The `interview_booked` event is the same (`via: chat`, actor `agent`).
- The model sees the source of every link, time and place it sent in a finished turn. A finished offer costs about 200 characters in the history instead of 22, a booking about 200, a Knockout about 150; turns after a booking are few.
- The skill grows by 310 characters, inside the prompt budget (`test_system_prompt_stays_small`).
- The stub model reads a slot `[tap result]` as a `book_interview` result; the Approval scenario asserts that the agent got the booking as its input.
- Tests: `tests/tools/test_tap_answer.py`, `tests/channel/test_booking_confirmation.py`, `tests/hermes/test_history_trim.py`, `tests/hermes/test_profiles.py`, `src/tests/sim/stub_llm/test_engine.py`, and `test_approval_offers_slots_and_a_tapped_slot_is_booked` in the scenario suite.
