# 0075. Recruiters see Jev's labels, never its scores

- Status: Accepted
- Date: 2026-10-12
- Refines: 0051, 0066 (and 0071 for who sees the intent)

## Context
ADR 0051 stores Jev's reading of each typed Candidate message and shows the Recruiter communication notes and, on the Application detail, `message_signals`: flags for the messages on which a signal fired or the language changed. ADR 0066 gave Operators the stored probabilities at `getJevReadings`, Operator only, and rejected an Operator-only field on the detail because "a role-gated probability on it is one serialisation slip from a Recruiter". ADR 0071 added an intent reading and a Manipulation score, Operators only.

The owner decided on 2026-10-12 that Recruiters should see, under each typed message they read in the conversation, what Jev read from it, as labels: the language, the signals that fired, the intent and the tone hint that was applied. No probability, bar, threshold, confidence or Manipulation score, in the API as in the UI. Operators keep the full panel. The same day the owner asked the Demo stage (`/stage`, Operator only, ADR 0052) to show the Operator readings under the record, a "View as" switch between the Recruiter's and the Operator's view, Approve from the stage, a Clear button on the Presenter console and an Agent activity timeline.

## Decision

### The labels, for every role
- **A new field on the Application detail, the same for every role**: `getApplication` gains `message_labels`, one `MessageLabel` per typed Candidate message Jev read (an `ok` row), oldest first. Spoken turns (ADR 0065), failed reads and messages with no row have no entry. This is not the field 0066 rejected: nothing on it is gated by role, because nothing on it is a score. Every role gets the same array and the same tests pin it, so there is no Operator-only value on the detail to slip.
- **Codes only, closed by the schema and by the query.** `MessageLabel` is closed (`additionalProperties: false`) with nine fields: `message_id`, `stage`, `at`, `language` (`es`, `en`, `other`, `unclear`), `fired`, `intent`, `tone_hint` (`apologise`, `simpler`, `offer_person`, `escalated`, `calm`), `language_set` and `language_reason` (`request` when the Candidate asked for a language). The only number is the message id. `present.message_labels_json` builds each label field by field from the stored row's code columns (through the existing `jev.store.list_signals`, so no new SQL and no new module names the table), and the tests pin the exact keys and search the wire for every stored score. Never Candidate text (0035).
- **What is withheld because it would read as a judgement of the person.** The `abusive` signal is never in `fired` (the label lists `frustrated`, `confused`, `wants_human` only), and the `steering` intent ("tries to give the assistant orders or change how it behaves", 0071) is sent as `null`. Both describe a message in Jev's terms, but a Recruiter reading "Abusive" or "Steering the agent" under a Candidate's message reads a verdict on the person. The other intents (`answering`, `asking`, `off_topic`, `wants_to_stop`, `other`) say what a message is doing, not what the person is. The schema's enums leave both codes out, so a server that sent them would fail conformance. The Escalation an abusive message raises is unchanged and stays in the queue, as before; `message_signals` (0051) and the `tone_hint` event are unchanged.
- **The intent is shown as Jev's top choice, without its confidence.** There is no display threshold: a 13th `JevThresholds` field would bump the policy version and cost every stored reading its markers (0071). A low-confidence intent can be wrong; it is a label for a person who decides, under the fixed line, and never an input.
- **The web app** puts a plain-text strip under each labelled typed Candidate message in the Transcript ("Spanish · Frustrated · Wants a person · Intent: Asking a question · Tone hint: offer a person · Asked for English"), with the fixed line "Communication context from the conversation, not an assessment of the Candidate." Codes become words through closed tables, so an unknown code or a number is never shown. No Tag, no colour. An Operator under "Preview as Recruiter" sees the strip and no Operator panel, as before.
- **Never a decision input.** Nothing that decides reads the labels: `present.py` was already on the guard's allow-list in `tests/jev/test_not_a_decision_input.py` for the flags, and the guard and its allow-list are unchanged.

### The Demo stage
- **View as.** The record pane gets a "View as: Operator | Recruiter" switch, Operator by default, remembered per tab in guarded `sessionStorage`. It is a presentation switch of this screen only: the server still sees the Operator, as with "Preview as Recruiter" (0052, 0066), whose behaviour is unchanged (an Operator previewing still gets Page not found on `/stage`). Recruiter shows the Recruiter's view of the record and, under it, the Message labels; no score and no Operator panel. Operator shows the record's two views and, under the record, two tabs: Agent activity and Jev readings.
- **Jev readings** under the record is the Application page's Operator panel itself, reused: no jump buttons (there is no Transcript on the stage) and no economics (no Cost card, no per-run tokens, cost or latency, ADR 0019).
- **Agent activity** is a timeline with one block per Candidate turn, newest at the bottom, under a one-line path legend. Per turn: the message in (typed, tap, spoken), Jev's reading with its scores and the call's latency and model, each agent run (Hermes profile, model, tokens, latency, cost, status), each tool call with its canonical arguments and what code decided (accepted, rejected with the validator's code, a Knockout), code's events that followed and the reply out. Every line is a stored record: the trace (`getToolCalls`), the readings (`getJevReadings`) and the detail's messages and events. A record is placed in the turn whose time window holds it (from one inbound Candidate message to the next); nothing is inferred beyond that and nothing is animated. The per-run cost is shown here, an Operator view, by owner decision. To make it possible the trace gains, additively and Operator only, each run's usage time, `hermes_profile` and `model`, and `jev_calls` (time, model, latency and status of the usage rows of kind `jev`, no reading). The jump from a reply to its phone bubble is not built: the phone's messages are the chat's, keyed differently.
- **Layout.** The record and the panel under it share the side column, the record about 58 % and the panel about 42 %, each scrolling on its own, so at 1920 by 1080 neither the phone nor the record is pushed off screen. The panel refreshes with the record (the same detail and stream, and the readings and the trace keyed on the message and event counts), with no polling of its own.
- **Approve on the stage.** When the Application is Qualified with an open Approval, the record pane shows Approve. It is the Review queue's call (`POST /api/queue/approvals/{id}`, decision `approved`, no note or confirmation, as the queue has none) as the logged-in Operator: a named person's decision (0012) through the same server path and checks, quiet hours included (0038). There is no new approval path.
- **Clear on the Presenter console.** Beside New take and Prepare take, disabled while a take runs, behind a confirm ("Clear the stage? Past takes stay on the dashboards."). It empties the stored Takes list and the phone and starts a fresh New take with a new phone. Client-side only: nothing is sent to the server and the Applications stay in the database and on the dashboards.

## Why this is lawful (the 0051 reading, unchanged)
- Not emotion recognition (AI Act Art. 5(1)(f)): text only, no biometric data; voice readings are not shown (0065).
- Never a decision input (GDPR Art. 22, AI Act Annex III point 4): no Knockout, Rejection, Approval, ranking, routing or booking reads the labels; the guard enforces it, and the Recruiter decides.
- Minimisation: labels instead of probabilities, no per-Candidate aggregate, no field a filter or sort can use, and the codes that read as a judgement of the person are withheld. Showing more to the Recruiter does bring the feature closer to the line 0051 describes; the mitigations above are why we read it as acceptable. Grupo Sazón's legal team confirms (the case brief, section 9).
- The privacy notice already says the hiring team sees the analysis "only as context for the conversation"; the language and "whether you need help or a person" are what the labels show. The intent label goes beyond those words; the owner's check of the notice for 0071's readings covers it, and this record does not change the copy.

## Alternatives considered
- **Extending `message_signals`.** Its entries exist only for messages on which something fired, by design ("calm" messages have none); the label must exist for every read message. Changing that meaning would change the Operator panel's flag rows.
- **A separate role-checked endpoint for Recruiters.** A second request per page for data every role may see; the detail already carries the Location scope and refreshes on the stream.
- **Showing the intent's confidence, or a display threshold.** Rejected: no numbers for Recruiters, and a threshold is a policy change (0071).
- **Showing `abusive` and `steering` in neutral words.** Any word for them still says what Jev thought the person was doing; leaving them out is the safer reading of "nothing that judges the person".
- **A new Operator endpoint for the Agent activity.** The existing trace held almost everything; three optional fields and one list were enough.

## Consequences
- Contract (additive): `MessageLabel` and `ApplicationDetail.message_labels`; `ToolCallRun.at`, `hermes_profile`, `model`, `ToolCallTrace.jev_calls` and `TraceJevCall`. `src/web/src/api/schema.d.ts` regenerated with openapi-typescript 7.13.0.
- The Demo stage now shows tokens and cost per run in Agent activity (Operator view). A recording that must hide cost uses View as Recruiter or the Jev readings tab.
- Tests: `tests/jev/test_labels_api.py` (labels per typed message, the exact keys and no score in the wire, `abusive` and `steering` withheld, spoken and failed reads left out, every role the same, an outside-Location Recruiter 404, the Operator's readings unchanged, the closed schema), `tests/api/test_tool_calls_api.py` (the new run fields and Jev calls), `tests/jev/test_not_a_decision_input.py` unchanged and green; web `message-labels.test.tsx`, `stage-record.test.tsx` and the Clear tests in `stage.test.tsx`.
