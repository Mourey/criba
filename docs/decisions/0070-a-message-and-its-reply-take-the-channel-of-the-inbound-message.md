# 0070. An Application keeps its channel; a message and its reply take the channel of the inbound message

- Status: Accepted
- Date: 2026-10-12
- Refines: 0021 (at most one open Application per Candidate), 0059 (voice is its own flow and channel), 0018 (the channel service stores and delivers), 0044 (code guarantees the AI disclosure), 0068 (the privacy notice link is guaranteed)

## Context
A Candidate has at most one open Application (0021), and the same person is found by phone on every channel. So a typed message in the web chat can reach an Application that started on a call (`channel = 'voice'`), and an utterance can reach one that started in the web chat. The inbound message was already stored on the channel it arrived on. Its reply was not: the sender stored every outbound message on the Application's channel. A typed message on a voice Application got a `voice` reply, which the chat never showed (the chat reads its conversation's channel), and an utterance on a text Application got a `webchat` reply that the spoken replay (which reads `voice` rows) could not find.

Two guards read the Application's channel too: the privacy notice link was skipped for any voice Application (0068), so the first written message to a Candidate who had called first carried no link; and a fixed message after an empty run (the Zone funnel's question) took no turn context at all.

The tension with 0059 is deliberate. 0059 rejected letting one Application mix voice and chat, because two flows writing one transcript showed a listener buttons and links. This record does not undo that: transcripts stay apart (a `voice` row is only ever spoken, a `webchat` row only typed), and no flow reads the other's messages as its own. What it accepts is that one Application, being one per Candidate (0021), can be worked by both flows in turn: a typed message on a voice Application runs on the text profile, an utterance on a text Application on the voice profile. The Hermes session is keyed by the Application id (0059, 0018), and each profile keeps its own session home, so the two profiles each hold a session under the same Application id and neither sees the other's history. The agent in each flow gets what it needs from the record (`get_application`), the same source both use for the Candidate's answers. This is accepted because the alternative is worse for the Candidate: a person who called and later types would either be refused, or start a second Application in the same funnel (0021 forbids it), and nothing else in the data model would change. A call is still not started on a text Application (0059). So a typed message on a voice Application can follow any call, while an utterance on a text Application can only arise mid-call: the voice Application closes (for example, a Knockout) and a typed message opens a new web-chat one, and the next utterance reaches it, because `_admit` in `channel/voice.py` does not check the Application's channel per turn. This record therefore narrows 0059's "out of scope" (continuing a text Application by voice) to "not started by us, but possible".

## Decision
- **An Application keeps the channel it started on.** A call does not move a text Application to voice, and a typed message does not move a voice Application to the web chat (0059). The channel stays where the Application's own behaviour needs it: no Approval message to a voice Application (`voice_no_messaging`), and the choices and tools that read `app.channel` today.
- **A message and its reply take the channel of the inbound message.** `accept_inbound` records the inbound's channel on the turn (`TurnRequest.channel`), and every reply to that turn is stored and delivered on it: the agent's reply, the fixed messages after an empty or failed run, the booking link of an "other time" tap, the Zone funnel's question, the unreadable-message hand-over, the opt-out confirmation, and the fixed spoken lines of a call. A fixed message owed after an empty spoken run is also said on the call, not only stored. `TurnRequest.channel` and `Sender.send`'s `channel` are required, so a new turn or reply site has to say which channel it answers on; the system turn after Approval, which no message prompted, names the Application's own.
- **Anything the Candidate did not just prompt uses the Application's channel,** spelled out at each call site: nudges, the Interview-offer template, the system turn after Approval, Team texts and notices. Those are a separate question (see Consequences).
- **The flow follows the message.** A typed message runs on the text profile with Jev before the run (0051), whatever the Application's channel. A spoken turn runs on the voice profile (0059). The Hermes session stays one per person per profile, keyed by the Application id (0008, 0059, 0018).
- **The disclosure and the notice follow the reply, not the Application.** `Router._disclosing` takes the privacy notice link from the reply's modality (typed: yes; spoken: no), never from the Application's channel: a typed reply on a voice Application is the Candidate's first written message and carries the link (0068). The AI disclosure is counted over every outbound message of the Application, so the disclosure spoken on a call counts as done for a later typed reply (0044): the typed reply does not repeat it, but it does add the link, which nothing on a call showed.

## Alternatives considered
- **Move the Application to the channel of the latest message:** the Application's channel decides which behaviour is right (no buttons or links on a call, no Approval message with no channel to carry it), and a Candidate who moves between a call and the chat would flip it back and forth.
- **Keep replies on the Application's channel and make the chat read all of a Candidate's messages:** it would show spoken lines in the chat transcript, which 0059 removed, and break the voice replay.
- **A default `channel` on `Sender.send`:** the original fix; it lets a new reply site forget the channel and quietly fall back to the Application's, which is how the funnel question and the privacy link guard were missed.

## Consequences
- The chat transcript holds only typed rows and the voice transcript only spoken ones, whichever channel the Application started on.
- Left to follow-ups, because they key on the Application's channel today: a Team text during a Takeover goes to the Application's channel, not the Candidate's latest one; the Zone funnel and the `[zone]` note are never offered on a voice Application, even for a typed message; "other time" gets no link on a voice Application, even for a typed tap (`_link_applies`); the `.ics` attachment is keyed on `INVITE_CHANNELS`; a nudge or Approval message does not reach a web-chat Candidate whose open Application is a voice one; and the WhatsApp window check reads the Application's channel.
