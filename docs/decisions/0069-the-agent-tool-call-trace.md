# 0069. Every agent tool call is recorded in `tool_calls`, linked to its run, and the Operator reads it

- Status: Accepted
- Date: 2026-10-12
- Refines: 0019, 0035

## Context
A tool call left no record. The backend served `POST /internal/tools/{name}` and returned, taking no timing and keeping nothing; the Hermes plugin timed the call but only logged it and dropped Hermes's `task_id`. An Operator looking at an Application could see the messages, the events and one `usage` row per run (ADR 0019), but not which tools the agent called in a run, how long they took or which failed. The run id reaches the backend only when the run returns (`messages.run_id` on the agent's replies, the run's `usage` row), so it is not known while a tool runs. Some arguments are free text (`search_zones.query`, every `note`, `record_answer.value` for `full_name`), and ADR 0035 keeps Candidate text out of anything that is not a message, a queue item or a hand-back.

## Decision
- **A `tool_calls` table** (migration 0012, `contracts/schema.sql`): one row per call with the Application, the run id and a `run_closed` mark, the tool, its start time, its duration in milliseconds, an outcome (`ok`, `invalid`, `knockout`, `error`), the error code and the arguments as JSON. `usage` is not touched: it stays one row per run, and a run's tokens and cost are read from it when the trace is served, not copied into each call.
- **What a row holds, and never holds.** Codes, ids, times and canonical values. Never a tool's `value` or `hint` (its result), a note, a search query, a name, a slot ref, the model's reasoning or message text. Arguments go through an allow-list: `get_application.language`, `search_zones.country`, `record_answer.field`, `raise_escalation.reason`, `record_backout.kind` and `offer_interview_slots.reschedule`, whose `tools.json` schemas are an enum or a boolean, are stored when the value satisfies its own schema. `record_answer.value` is the one other exception: stored when the call was accepted (`ok` or `knockout`), the field is not `full_name` and the value has the field's structured shape (ADR 0042). Every other key is stored as its name with a null value, a value that fails its schema is stored null, and a key the tool does not take is dropped. A test reads `tools.json` and fails if an allow-listed key stops being an enum or a boolean, and another routes the scripted journeys of the no-free-text test through the HTTP endpoint and looks for the Candidate's words in the stored arguments.
- **Outcome mapping.** `ok` for an `ok: true` result, except a Knockout: `record_answer` returns it as `ok: true` with `value.status == "knockout"`, and the row is `knockout`, not an error. `invalid` for `invalid_args` and `invalid_value`. `error` for every other error code. The error code is stored for `invalid` and `error`.
- **Only calls through `/internal/tools` are recorded.** A tap that the backend applies itself calls `call_tool` directly (`tools/choices.py`); it is the Candidate's choice, already stored as a message and events, and is not an agent call. Requests refused before dispatch (bad secret, unknown tool, oversize body, the envelope's 422) and calls on an unknown session leave no row.
- **Best effort, off the response.** The row is written after `call_tool` returns, on its own connection and transaction, waiting at most 250 ms for the writer lock, and only if the Application exists. A failed or slow write is logged without arguments and swallowed: the tool's response, status code and the `after_call` task are unchanged. Measured over 100 calls, the write adds about 1 to 3 ms at the median, so it stays on the request path; the 5 ms threshold for moving it to the background slot was not reached.
- **Linking by run window.** The router records the time before each run starts, on the typed and the spoken path. When the run returns (right after its `usage` row) or fails, it sets the run's id on the Application's rows that have no run id, are not closed and started between the run's start and that moment. A failure with no run id marks those rows `run_closed = 1` instead, so a later run never claims them. A failure that came before the run started closes nothing. Runs are serialised per Application, so windows on one Application do not overlap. Linking is best effort too: a failure to link is logged and leaves the reply, the `usage` row and the `run_error` handling as they are.
- **A late call stays unlinked, with one exception.** A call that arrives after its run's window closed (a timed-out run still calling tools in Hermes) stays unlinked and is shown as such, unless it lands inside a later run's window, where it is linked to that run: `started_at` has one-second resolution, so a late call in the same second the next run starts, or during it, cannot be told apart from that run's own. The row's `started_at` and `duration_ms` stay true either way. Late calls are rare, and a tighter link needs the option not taken below.
- **Retention and deletion.** The scheduler purges rows older than the `message_signals` retention (`CRIBA_SIGNALS_RETENTION_DAYS`, default 180) on each tick, in its own `try`, so a failed purge stops nothing else. A row goes with its Application (`ON DELETE CASCADE`).
- **Erasure: an accepted gap.** Erasure deletes nothing in the system today: a `record_backout` with `erasure_request` only sets `candidates.erasure_requested_at` and adds an event (`tools/application.py:742-757`). Until Erasure is implemented, an Erasure request removes no trace rows, as it removes no messages. The cascade makes the trace go when its Application is deleted, which is the part this decision delivers. The owner accepted the gap on 2026-10-11.
- **An Operator-only endpoint.** `GET /api/applications/{application_id}/tool-calls` returns the runs oldest first, each with its status, tokens, cost and latency from its `kind = 'run'` usage row and the ids of the agent replies that carry its run id, then a last group with a null `run_id` for the calls no run claimed. A run with calls and no `usage` row (its usage write failed) is listed with null numbers. A Recruiter gets 403, an anonymous caller 401 and an unknown Application 404. It returns ids, codes, numbers and the stored arguments, and `getApplication` is unchanged.

## Alternatives considered
- **Extending `usage`:** it is one row per run by design (`usage_one_row_per_run`); a row per call would break the ledger's counts.
- **Forwarding Hermes's `task_id` through the plugin:** it would link a call to its run at write time, but it widens the tool envelope and the plugin, changes `tools.json`, and rests on unverified Hermes behaviour (whether `task_id` is the run id). Not taken; revisit if late calls prove common.
- **Copying tokens and cost into each row:** they would be written before the run's `usage` row exists. They are read from `usage` when served.
- **Storing the tool's result or a hash of the arguments:** the result carries hints and Candidate-derived values, and a hash of free text is still derived from it.

## Consequences
- The Operator can see, per run, which tools the agent called, in what order, how long each took, whether it was accepted, and what the run cost.
- Rows can be lost under writer-lock contention (the trace waits 250 ms, then gives up); completeness is measured in a test, not guaranteed.
- A late call can be linked to the wrong run only in the same second a later run starts or during it.
- Until Erasure is implemented, trace rows outlive an Erasure request, up to 180 days.
- `contracts/schema.sql` and `contracts/api.openapi.yaml` change in separate commits (lanes A and D), and `schema.d.ts` is regenerated for the web panel that reads the endpoint.
