# 0059. Voice is its own flow: its own channel, Hermes profile and Screener skill

- Status: Accepted
- Date: 2026-10-11
- Supersedes: 0031 in part ("voice is a channel adapter" of the chat, and "one Application can mix voice and chat"); the voice log's decisions 3 and 17 (the voice agent log: the voice rules and the rule-1 exception travel in the run input) and the rule text of decision 64
- Refines: 0008 (a profile per client-facing role), 0018 (the channel service calls Hermes), 0041 (skills reach the agent through `SOUL.md`), 0044 (the AI disclosure)

## Context
The voice agent shipped as a mode of the web chat. A call started from a web chat conversation; each spoken turn went to the text Screener profile (`criba-recruiter`) with the voice rules (`VOICE_TURN_RULES`) written into the run input, because the Screener skill sits at its prompt cap (decisions 3 and 17). Spoken replies were stored in the chat transcript as `webchat` messages with `modality = 'spoken'`.

The first real calls showed the agent kept behaving like the chat: it pointed to links and buttons, said "por aquí", retyped or invented options, narrated its own corrections and repeated the AI disclosure that the call had already spoken. A dozen per-turn override rules on top of a skill written for text did not hold: every line of the text skill still pulled the other way, and decision 64 had to keep growing the rule list. The owner decided on 2026-10-11 that voice and text are separate flows.

## Decision
- **Its own Hermes profile.** `criba-recruiter-voice` (`src/hermes/profiles/criba-recruiter-voice/`) has the same lean toolset (only `criba-tools`), memory and session search off, the same model and the same pinned auxiliary settings as `criba-recruiter`. Its identity (`SOUL.md`) says the Candidate is on a voice call. A sim variant, `criba-recruiter-voice-sim`, differs from it only in the model (the stub), as `criba-recruiter-sim` does from `criba-recruiter`.
- **Its own Screener skill, written for speech.** `src/skills/criba/voice-screener/SKILL.md` carries the same screening procedure and tool use as the text Screener, rewritten for a listener: plain spoken sentences; no emoji, markdown, lists or URLs; never a chat, link, button, writing or "por aquí"; pending options read aloud, naming only options from the record; no narration of the system or of its own corrections; the summary as sentences; a short spoken privacy notice; a spoken booking read-back (day, hour, place); "se pondrá en contacto contigo" for next steps; and no second AI disclosure, because the backend speaks it first (0044, voice spec R17). It reaches the agent through `SOUL.md` and `skills.txt` like any skill (0041). Placeholder copy stays marked SYNTHETIC.
- **No voice rules in the run input.** A spoken turn's input keeps the `[application]` block and its rule (the agent does not call `get_application` on that turn), a bare `[voice]` marker and `[optout_request]` when the spoken checks set it, then the utterance. Nothing sends `VOICE_TURN_RULES` (`criba/channel/voice_rules.py`) any more; what it said now lives in the voice skill. Deleting the module also deletes its test, which needs an owner-approved floor exception, so it stays until then.
- **Its own channel and Hermes session.** Spoken turns run on `/p/criba-recruiter-voice/v1/runs` (`CRIBA_HERMES_VOICE_PROFILE`; the sim stack sets the `-voice-sim` profile, and the backend refuses a sim/production mismatch on either profile at startup, 0036). The session id is still the Application id; Hermes keeps each profile's sessions in its own home, so the voice session never shares history with a text one. Messages, the Candidate identity and the Application a call starts are recorded with `channel = 'voice'`; the sender has a `voice` adapter that stores without delivering, like web chat's.
- **A voice-only entry point.** `POST /api/chat/conversations` takes `channel: voice` and starts a voice conversation (a `voice` identity; its id is used as before). Its transcript is read with the same `GET` endpoints; it takes no typed message or tap (404). `POST .../voice-session` starts a call only on a voice conversation: a web chat conversation, or a Candidate whose open Application is not a voice Application, gets the generic 409 `voice_refused`. Typed chat on `/test-chat` is unchanged.
- **Shared and unchanged:** the tools, validators, Knockouts (with the spoken Knockout and Qualified copy of decision 64), Approval, Takeover, Jev, the cost ledger (spoken runs are recorded under the voice profile) and the data model. Still one open Application per Candidate.
- **After Approval** a voice Application gets no system turn and no template: there is no channel to reach the Candidate on, so the router answers `none` (`voice_no_messaging`). On their next call the agent sees `approved` in the record and offers slots aloud.

## Alternatives considered
- **Keep one profile and grow the per-turn voice rules** (decisions 3, 17, 64): the rules fight a skill written for text on every line, cost input tokens on every spoken turn, and were already failing on real calls.
- **Raise the Screener's prompt cap and add a voice section to it:** both flows pay for each other's text on every turn, and the text skill's chat rules still reach the voice agent.
- **Let one Application mix voice and chat** (0031): two flows writing one transcript, with buttons and links that a listener never sees. Continuing a text Application by voice is out of scope.

## Consequences
- Two skills carry the same procedure. A change to the procedure (a field, a tool, a Knockout rule) has to be made in both; `src/backend/tests/hermes/test_profiles.py` checks that both name every tool and the same field names, and that each profile lists its own skill.
- There is no separate spec for this change: this record, the architecture diagrams and `CONTEXT.md` (**Voice call**) are updated together, and the voice spec's rows that say voice runs on the chat profile (R10, R11) are superseded here.
- The `/test-chat` voice button now gets the 409. A voice page (`/voice`) that starts a voice conversation is the web app's next step.
- **Open question (needs a messaging channel):** a voice-only Candidate hears a short privacy notice and a spoken booking read-back, but gets no written follow-up: no full privacy notice, no `.ics` invite, no Stalled nudge they can see (nudges are stored on the `voice` channel and never delivered), and no Approval message between calls. Asking for a phone number or email on the call, and which channel then carries the follow-up, is for the owner.
- An Application reopened within 30 days (Abandoned, or a Knockout dispute) keeps the channel it started on; a voice call does not move a text Application to voice.
