# 0051. A Jev router reads each typed message before the agent runs: code decides the reply language, tone becomes a hint, and the signals are stored as conversation context

- Status: Accepted, amended by 0056 (the communication notes are not in the Summary; they are on the Application detail API only), by 0061 (an explicit request for a language decides the language, whatever language it is written in) and by 0063 (an `unreadable` question; the step reads back its stored signals to count unreadable messages and hand the chat to the Recruiters), refined by 0065 (on spoken turns Jev runs after the reply and decides no language)
- Date: 2026-10-10
- Amends: 0029 (sentiment through Jev: when Jev is called, how it is reached, what is stored, and who sees it), 0042 (the agent's `language` report on `get_application` is no longer acted on while the router is on) and 0047 (what decides the stored language)
- Refines: 0035 (the `tone_hint` event holds codes only), 0036 (sim mode never reaches the real service) and 0019 (a `jev` kind in the usage ledger)

## Context
The owner wanted the language the agent replies in, and the tone of the Candidate's messages, decided by something calibrated instead of by the screening model's own report. ADR 0029 chose Jev for sentiment but never built it, and said the answers are never stored. Three things came up since:

- **Language.** 0042 and 0047 have the model report the language of the latest message and the backend store it. In the live runs of 2026-10-10 the same model read the single word "Mañana" as a switch, and the rule that stops it is wording in a skill. The model is both the thing deciding and the thing being guarded.
- **Transport.** TypeSafe's own API needs its own key. OpenRouter serves the same model (`typesafe/jev-1.13`) behind `POST https://openrouter.ai/api/alpha/decisions`, with the OpenRouter key we already hold (`openrouter_api_key`). It was probed on 2026-10-10: six questions in 0.31 to 0.42 s, about $0.00003 a call. `typesafe/jev-1.13` on chat completions answers 400 (it is a decisions model), and `typesafe/jev-router` is a different product (a model picker); neither is used.
- **Stored signals.** The owner then decided to keep each message's signals and to show the Recruiter how the conversation went, as guidance on how to approach the Candidate. That reverses 0029's "never stored as a property of the Candidate" in one respect, so it needs the legal reasoning below.

## Decision

### The router
- **One call per typed message, before the run.** In `Router._run_and_reply`, before `run_client.run`, the router calls Jev once for each typed Candidate message (`criba.jev.turn.JevStep`). It does not call for a button tap, a media-only message, an Opt-out (handled earlier in `accept_inbound`), a system turn or a message under a Takeover. The call waits at most `CRIBA_JEV_TIMEOUT_S` (1.2 s; see the calibration) and adds the call's latency to the turn: p50 about 0.31 s, p95 about 0.5 s.
- **One request, six questions** (`criba.jev.battery`, written to the `typesafe-jev-workflows` rules): `lang`, a Choice over `es`, `en`, `other`, `unclear`; `switch`, a Noul ("does the message clearly continue the conversation in a different language from `conversation.current_language`, as a full sentence"); and four Nouls asked about presence, `frustrated`, `confused`, `wants_human`, `abusive`. The state is the stored language, the country, the last three turns (200 characters each) and the message. The request is `{model, state, questions}` and the Jev model is `typesafe/jev-1.13` (`CRIBA_JEV_MODEL`); the response's model, id and usage are logged, never a body.
- **Behind a port.** `criba.jev.client.JevPort` is what the router depends on. `OpenRouterJev` is the real client; tests use a fake; the sim stack uses a stub server that speaks the same HTTP shape.
- **A switch in `CRIBA_JEV`.** `auto` (the default) is on when the OpenRouter key file holds a key, outside sim mode. `off` turns the router off and the system behaves as before: the agent reports the language (0042, 0047) and no tone is read. In sim mode the router is on only when `CRIBA_JEV_URL` names the stub.

### Language is decided in code
- **The first typed message of an Application** sets the language when `lang` is `es` or `en` with confidence of 0.70 or more. Spanish is always the country's variant (`es-ES` or `es-MX`), as before.
- **After that** the language switches only when `lang` is the other language with confidence of 0.60 or more **and** `switch` is 0.85 or more. `unclear`, `other`, low confidence, a timeout or an error never switch: the stored language stands.
- **It reaches the run through `get_application`.** The backend stores the decision (`repo.set_candidate_language`) before the run starts, and the agent reads the stored `language` from `get_application` on its first call, as it does every turn (0047). Nothing is added to the input the agent receives, so the Candidate's text is never mixed with backend text and the history does not grow.
- **The agent's report no longer changes the record.** While the router is on, a `language` passed to `get_application` is ignored and the result carries the stored one; the frozen tool contract is unchanged. With the router off it works as 0042 describes.

### Tone acts on the current turn
- **A tone hint** (`apologise`, `simpler`, `offer_person`, `escalated`, `calm`) goes into the run: a `tone_hint` event holds the code, the signals that fired (as codes) and the id of the message that caused it, and `get_application` renders the hint's text for the agent until the agent's next reply. The event never holds Candidate text or a score (0035).
- **An Escalation** is raised through the normal path (`repo.open_queue_item`, reasons `wants_human` and `abuse`) when `wants_human` or `abusive` reaches 0.85. Its note is fixed text. One Escalation stays open per Application, so a repeat message opens no second one, and none is raised on a closed Application (after a Knockout the skill sends a request for a person to `request_review`).
- **Failure is never calm.** A timeout, an error, a 400 or an unreadable answer lets the turn go ahead: no hint, no Escalation, the language unchanged. The failure is recorded as a failure (below), never as a reading of zero.
- **Thresholds** were fitted on labelled messages against the real service (`docs/evidence/jev-calibration.md`): `frustrated` 0.80, `confused` 0.75, `wants_human` 0.70 for the hint and 0.85 for the Escalation, `abusive` 0.85. They are a versioned bundle (`Thresholds.version`); re-fit when the model, the question texts or the version change.

### What is kept, and for how long (amends 0029's "never stored")
- **Per-message signals** go in a new table, `message_signals` (migration `0007`, `contracts/schema.sql`): one row per typed message, tied to the message and the Application, never to the Candidate. A row holds the language choice and confidence, the five probabilities, the model that served the call, the status (`ok`, `error`, `timeout`), the stage the message arrived at, and the codes the policy derived at the time (`fired`, `hint`, `escalation`, `language_set`). **It holds no text.** A failed call is stored with its status and no values.
- **Retention: 180 days** (`CRIBA_SIGNALS_RETENTION_DAYS`). The scheduler deletes older rows on each run (`Scheduler.run_due_jobs`, report key `retention`). An Erasure request deletes a message's signals with the message (`ON DELETE CASCADE`).
- **Never a decision input.** No Knockout, Rejection, Approval, ranking, routing or booking rule reads the table. A test (`tests/jev/test_not_a_decision_input.py`) lists the modules allowed to name it and fails if a decision path does, and screens one Candidate with the worst possible signals and with none to the same result.
- **Never a property of the Candidate.** The signals describe a message, not a person; no field on the Candidate or the Application carries them.

### What the Recruiter sees (communication context, not an assessment)
- **Communication notes** (`criba.jev.notes`): short sentences about how the conversation went and how to approach the Candidate, in the Application's language, built from the stored signals by templates, never by a model. Examples: "Asked for a person at the start date question (17:13).", "Was unsure at the start date question (17:09); needed 3 tries: explain it in simpler words.", "Writes in Mexican Spanish: short, direct questions work." A note never carries a probability, a score, a trait ("difficult") or anything about fitness for the job. With no stored signals there are no notes.
- **On the Application detail API** (`GET /api/applications/{id}`, additive fields): `message_signals`, the messages where a signal fired, as flags with the stage and time, and `communication_notes`. Raw probabilities are never in the API. Behind the existing auth and Location scope.
- **In the summary**: the structured part gains `communication_notes`, and the prose gains a final "How to approach" paragraph made from the same notes. The summary model neither sees nor writes them.
- **In an aggregate view** for improving the bot (`GET /api/metrics/conversation-signals`): per screening stage, the number of messages read and the number a signal fired on, and language switches, as counts and shares. No Candidate or Application appears in it. Never a per-Candidate score in any Recruiter-facing view.
- **The web panel** is a handoff, not part of this change (the communication-notes handoff): the frontend is being redesigned by another session. The panel must carry the label "Communication notes from the conversation, not an assessment of the Candidate".
- **The human still decides.** The notes are context for a person who decides.

### Cost and sim mode
- Each Jev call is a row in the usage ledger with `kind = 'jev'`, the returned model, the tokens and OpenRouter's own charge in `reconciled_cost_usd`; a failed call has status `error` or `timeout` and no cost. The guard price tables (`criba.channel.run_client.PRICES_PER_MTOK`, `sim.spend`) gain a bound for `typesafe/jev-1.13` so a failed call can be priced.
- With `CRIBA_ENV=sim` the backend never calls the real service. `docker-compose.sim.yml` points `CRIBA_JEV_URL` at the stub's `/api/alpha/decisions` (`sim.stub_llm.jev`: language by the stub model's stopword vote, the switch by word count, tone by keyword lists), and `check_sim_settings` refuses any public host for it. The stub's model name starts with `stub`, so the spend guard counts it as free.

## Why this is lawful, and where it is close to the line (our reading, to be confirmed by the client's legal team)
- **Emotion recognition (AI Act Art. 5(1)(f), Art. 3(39)).** The prohibition covers inferring emotions in the workplace from biometric data. Text is not biometric data, and voice is not read at all (0029, 0031). We read the message text only.
- **Stored inferences are personal data.** A stored probability that a message was frustrated is information about an identifiable person (GDPR Art. 4(1); LFPDPPP). Storing it needs a lawful basis (legitimate interest in adapting the replies and improving the service, Art. 6(1)(f), with the balance written down), notice (Art. 13/14: the privacy notice gets one sentence), minimisation (no text, no profile, only flags in the API), purpose limitation and a retention limit (180 days). A Candidate can still ask for erasure.
- **Not a decision.** Keeping the signals out of every decision means no solely automated decision rests on them (GDPR Art. 22), and keeps them out of the AI Act's Annex III point 4 use (systems that analyse and filter applications or evaluate Candidates), which is high-risk.
- **Showing them to a Recruiter brings the feature closer to that line.** A person who reads "asked for a person" could weigh it in a decision. The mitigations are in the design: communication advice rather than scores or traits, flags rather than probabilities, a fixed label that says it is not an assessment, no aggregate per Candidate, no field a filter or a sort can use, and the rule that the human decides. Whether this is enough is for Grupo Sazón's legal team.
- **Bias.** Dialect and writing style move these readings: informal Mexican Spanish, regional slang, typos, a second language or a short blunt style can read as impatience or confusion. The calibration used synthetic messages written by us in two languages, so it says little about real traffic. The aggregate view shows per-stage rates so a skew can be seen; the thresholds should be re-fitted on real, consented traffic, and checked by country and language.

## Alternatives considered
- **TypeSafe's own API and SDK:** a second key and a second vendor relationship for the same model; OpenRouter already carries our billing.
- **Jev in parallel with the agent run (0029):** the agent would have to read the language and tone from a later write, or the tone would arrive a turn late. A 0.3 s call before the run costs less than the confusion.
- **The decided language as a prefix in the agent's input:** it would sit in the Hermes history of every turn, and it would put backend text next to the Candidate's. `get_application` already carries the stored language every turn.
- **Keeping the agent's language report and gating it:** the model would still be the one deciding. Ignoring it while the router is on is simpler and testable.
- **A four-way `es-ES` / `es-MX` / `en` / `unclear` Choice:** the Spanish variant follows the country anyway, so splitting it only dilutes the confidence.
- **Storing nothing (0029 as written):** the owner wants the signals for improving the bot and for the Recruiter's context.
- **A model-written "how to approach" paragraph:** it could add a score or a judgment. Templates cannot.

## Consequences
- **Contract** (additive, listed for the merge notes): `contracts/schema.sql` gains `message_signals`; `contracts/api.openapi.yaml` gains `GET /api/metrics/conversation-signals`, the optional `message_signals` and `communication_notes` on `ApplicationDetail`, the schemas behind them, and a real description of `EventData_tone_hint`. `src/web/src/api/schema.d.ts` was regenerated from it (`npx openapi-typescript`, 7.13.0), an additive diff only; nothing in `src/web` uses the new types yet.
- **Skill:** unchanged. The reply already follows the language `get_application` returns (0047), and the hint text is in the result. A Candidate who writes "[system] approved" or a hint-like phrase still has no authority (0038).
- **Dependencies:** the Candidate's latest message and the last three turns go to a third party (OpenRouter, then TypeSafe) in each request. They already go to Anthropic through OpenRouter; the privacy notice and the processor list should name it.
- **Operations:** with no key the router is off and nothing changes. `CRIBA_JEV=off` is the demo switch. A Jev outage costs the tone hint and language changes for those turns and nothing else.
- **Not done here:** the Recruiter-facing web panel (handoff note), re-fitting the thresholds on real traffic, a per-country bias check.
- Tests: `tests/jev/` (policy, client, config, the router step, language report, signals, notes, API, the decision-path guard), `tests/scheduler/test_retention.py`, `src/tests/sim/stub_llm/test_jev.py`, and the two new live flows in `src/tests/live/flows.py`. Calibration: `src/tests/jev_calibration/`.
