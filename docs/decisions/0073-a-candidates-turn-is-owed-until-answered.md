# 0073. A Candidate's turn is owed until it is answered, and a failed turn is retried

- Status: Accepted
- Date: 2026-10-12
- Refines: 0018 (the router and the Runs API), 0019 (one usage row per run), 0020 (Takeover), 0039 (what the scheduler holds), 0051 (the Jev step), 0064 (the "other time" link after a failed run), 0065 (spoken turns)

## Context
An error-handling audit for the case requirement "graceful failures" (lane A, owner-approved 2026-10-12) found that a Candidate's turn could be lost when Hermes or the model went down mid-chat:

1. **A failed turn was never retried.** The router sent "dame un momento", opened a `technical_error` Escalation and stopped. On a sim stack, once Hermes came back, the Candidate's next message ("Madrid, Chamberí") was taken as the answer to the lost name question and the Application stuck at `greeting` (`run_error`, `escalation_raised`, `answer_invalid`).
2. **A restart mid-turn lost it silently.** The web chat runs a turn as a FastAPI background task, held only in memory. The inbound message was committed, but nothing at startup looked for unanswered messages: no fallback, no Escalation. The Stalled ladder then nudged a Candidate who was waiting on us, and could end the Application as Abandoned.
3. **A provider outage made the Candidate wait 60 s.** Hermes v0.21.6 retries each model call 3 times and then waits out up to 5 recovery cycles of 15/30/60/60/60 s (`agent.auto_recovery_cycles`, `agent/turn_recovery_autorecover.py`), so the run stayed `running` past our 60 s timeout, although the connect errors were known within about 200 ms.
4. **A POST that timed out after Hermes took the run was reported as "unreachable".** Hermes could finish the run (and its tools write answers), but the reply was never delivered.

Two Hermes facts shape the design (`gateway/platforms/api_server_runs.py`, `api_server_run_idempotency.py`). A re-POST under the same `Idempotency-Key` replays the run Hermes took, whatever its status, for 24 hours. And the key is bound to a fingerprint of the request body, so the same key with a different input is a 409.

## Decision
- **An owed turn is a durable record.** A new table, `owed_turns` (migration 0015, `contracts/schema.sql`), holds one row per typed Candidate message on the web chat or WhatsApp that starts a run. The router writes it when it accepts the message and deletes it once the turn is answered: the reply was sent, the run ended with nothing to send, the reply was dropped by a Takeover, or the chat went to the Recruiters (0063). The row keeps what a later attempt needs to run the same turn: the turn input; the exact input first POSTed and the key it went under; the tap's `after_event_id` and the "other time" link; the number of failed attempts; the next attempt time; whether the holding message went out; and `owed` or `exhausted`. The run input is Candidate text, so a row is deleted with its message (`ON DELETE CASCADE`), and it lives only while the reply is owed.
- **A failed attempt is retried after 15 s, 45 s and 2 min.** The recovery is `Channel.resume_owed_turns`. The scheduler calls it on its own 5-second loop: first at startup, with every owed turn the last process left, whatever its lease, then with the turns whose next attempt is due. Every `run_due_jobs` tick calls it too, so the sim clock reaches it. A fresh row has a lease of the run timeout plus 60 s: while the accepting request still runs the turn, the recovery leaves it alone, and it also skips an Application whose turn is queued or running in this process. Each Application's owed turns run oldest first, on a thread of their own, under its turn lock.
- **Same key, same bytes, nothing runs twice.** A retry POSTs the stored input under the stored key. If the earlier attempt reached Hermes (a timeout while the run was still going, a lost POST answer, a restart mid-run), Hermes answers with that same run. Only when Hermes reported the run over and failed (a terminal status or event, or a 4xx), where its key would replay the failure, does the next attempt take a new key, `<message_id>~r<n>`. That run is finished, so the new key cannot double it. The run client also re-POSTs once at once under the same key when a POST's answer is lost (item 4).
- **The holding message goes out once per outage; the Escalation opens when the retries are spent.** The first failure sends "dame un momento" (or, for an "other time" tap, the booking link, 0064) and marks the Application's owed turns. Later failures send nothing until a turn is answered. The `technical_error` Escalation opens when the fourth attempt fails, about three minutes after the first. A failure that is retried and then succeeds is not one Recruiters need to act on. Spec 002 asks for "a 'dame un momento' message plus an Escalation", and 0020 and 0039 set no timing, so the Escalation still comes, after the retries. Each attempt's failure is still a `run_error` event and a failed usage row. An exhausted turn gets no more automatic attempts. The Candidate's next message runs it first, and a Recruiter can take over.
- **Order is kept.** The router runs one turn per message, one at a time per Application, and has no batching. A message that arrives while older turns are owed therefore runs them first, in order, then itself. If an owed turn fails again, the new message waits behind it, owed too, and no second holding message goes out. The sim's lost name question is answered before "Madrid, Chamberí" is read.
- **Nothing is counted or read twice.** A retry reuses the Jev reading of the first attempt, together with its language, tone and unreadable count: the step runs before the input is stored, and a stored input means the step ran. A success that follows a failed attempt of the same run replaces that attempt's usage row instead of adding one (0019: one row per run).
- **The Stalled clock stops while a reply is owed.** The Stalled ladder skips an Application with an `owed` turn, or with an `exhausted` turn while an Escalation of the Application is open. No nudge goes out and nothing turns Abandoned while the Candidate waits on us. Once the Escalation is dismissed, the ladder runs again.
- **A Takeover drops the owed turns.** Starting a Takeover deletes them, and the router drops them whenever it finds `control = 'human'` or the conversation with the Recruiters (0020, 0063). Nothing is retried into a conversation a person holds.
- **Quiet hours do not apply.** A retry answers the Candidate's own message, so it goes out like any reply (`proactive=False`). 0038 and 0039 hold only what we start: nudges and the turn after Approval.
- **Fail fast where the failure is knowable.** The Hermes profiles set `agent.api_max_retries: 2` and `agent.auto_recovery_cycles: 0` (keys read at `agent/agent_init.py:1434-1445`). A provider outage then fails the run in a few seconds, and the backend's retries take over. The run client fails at once on a refused connection, and ends a poll that has not reached Hermes for 5 s. A run Hermes still reports as running is polled to the 60 s timeout as before, so a slow run is never cut short.
- **Scope.** The web chat and the WhatsApp channel (no adapter yet; any adapter that goes through `accept_inbound` and `run_turn` gets this) owe their turns. A spoken turn is never owed: a reply cannot reach a call that has moved on (0065). A spoken failure keeps the fallback line and the immediate Escalation, as does the system turn after Approval, which no Candidate message prompted.

## Alternatives considered
- **Derive the owed state from `messages` and `run_error` events, with no new table.** That needs no contract change. But a tap's recorded result could not be rebuilt for the retry, the holding message looks like an answer, and a run that ended with no output looks unanswered forever.
- **A new key on every retry.** Simpler, but a run Hermes took and finished (a timeout, a lost POST answer, a restart mid-run) would run twice, and its tools would write twice.
- **Coalesce the owed and the new messages into one run.** One reply instead of two, but it needs a new key, so a run Hermes already took would be repeated. It also departs from the one-turn-per-message order the router keeps.
- **Keep opening the Escalation at the first failure.** Recruiters would see every short blip that the next retry fixes.
- **Retry inside the request with sleeps.** Lost on a restart, and it would hold a worker thread for minutes.

## Consequences
- A Hermes or model outage of under about three minutes costs the Candidate one holding message and a late reply, and no Escalation. A longer one escalates once.
- A restart loses no turn: the startup pass answers what the last process accepted.
- The Candidate may get two replies in a row after an outage, one per message, as when they type two messages quickly.
- `contracts/schema.sql` gains `owed_turns`. The `run_error` payload is unchanged.
- The Hermes image must be rebuilt for the profile settings (`docker compose build hermes`).
- Known limits: a restart between the Jev step and the stored input calls Jev again for that message. After the Escalation is dismissed, an exhausted turn waits for the Candidate's next message. The Stalled clock still measures silence from the Candidate's last message, so a Candidate answered late may get the first nudge soon after the reply. Hermes may keep the failed attempt's user message in its session, so a retry under a new key can show the model the message twice.
